# Phase 0 Research: 专户产品净收入比例录入（高保真原型）

**Date**: 2026-09-21 | **Plan**: [plan.md](./plan.md)

Technical Context 无遗留 NEEDS CLARIFICATION（交付形态已由用户定夺为高保真交互原型）。以下为影响设计的关键技术/口径决策，按「Decision / Rationale / Alternatives」记录。

## D1. 交付物形态：新建单文件原型，不改既有定稿原型

- **Decision**: 新增 `项目/净收入比例录入/prototypes/净收入比例录入原型.html`；既有《归属比例配置流程原型.html》（20260909 定稿版）与《净收入拆分系统原型.html》保持原样，分别作为交互基线与规则链移植来源。
- **Rationale**: 定稿版是历史评审留档，改动破坏可追溯性；新 spec 行为增量（预览、互斥、漏设高亮、版本对照）过大，重写比缝补干净；单文件约定与 prototypes/ 现状一致，双击即演示、可邮件分发。
- **Alternatives considered**:
  - 在既有配置流程原型上迭代——否，定稿版留档价值高于复用价值；
  - 多文件工程（Vite + 组件化）——否，违背离线单文件约定，评审分发成本高；
  - 全栈应用——否，用户已明确排除（2026-09-21 定夺）。

## D2. 预览规则链：从拆分原型移植 R1–R3/R5/R6 计算函数

- **Decision**: 将《净收入拆分系统原型.html》中 `calcProduct`/`pct` 等规则链 JS（R1 直销组内占比、R2 代销筛选拆分、R3 混合加权合成、R5 占比×净收入总额、R6 ×(1−总部份额)）移植进新原型，作为 FR-016/017「同一规则口径」的唯一实现；预览仅调用该链路对**上月净收入（总）**试算，结果只渲染不落库（不写入产品现行配置）。
- **Rationale**: FR-017 要求「所见即所拆」——两份原型若各写一套算法必然漂移；拆分原型已按 ADR-0001 与 Q14（4 位小数、尾差计最大方）实现并经评审。
- **Alternatives considered**:
  - 预览只展示比例条形图（旧原型 splitBar 水平）——否，不满足 FR-016「对上月净收入试算各归属主体份额」；
  - iframe 嵌入拆分原型——否，file:// 下跨文件状态同步脆弱，且拆分原型是月度批量视角、非单产品编辑视角。

## D3. 预览数据前提与降级（FR-018、E-g）

- **Decision**: mock 数据内置「上月净收入（总）」表；三种降级态：① 产品无净收入行 → 预览区显示「暂无可预览数据：该产品上月净收入未上传」；② 银行部产品总管理费为 0 → 参考值区显示「参考值不可用」（E-g 关联，不空白不报错）；③ 预览结果恒带「试算值」水印/角标，页脚声明不被下游引用。
- **Rationale**: FR-018 明确不阻塞录入流程；E-g 在例子表待确认清单中，原型按「显示不可用」的建议默认演示，定稿后若出入再改。
- **Alternatives considered**: 隐藏预览区——否，「显示原因」是 FR-018 的验收点。

## D4. 流程引擎：声明式场景表 + 步骤轨道（延续既有原型模式）

- **Decision**: 沿用既有原型的 `SCN` 声明式场景结构（每场景 = 步骤数组，每步含 who/渲染器/校验器），扩展支持：退回带意见（rejectReason 入留痕）、多级确认链（部门间调整的涉事部门逐一确认）、审批环节（银行部/机构券商部门内调整）。四场景：首次确认、银行部总部份额、机构券商部门内、部门间。
- **Rationale**: 该模式已在 20260909 定稿版验证过评审可用性；声明式步骤让「当前环节 + 可执行动作」一目了然，直接对应 spec 的流程单实体（场景/发起人/当前环节/状态）。
- **Alternatives considered**: 引入状态机库（XState）——否，违背无依赖约定，四个场景的复杂度用数组+枚举足够。

## D5. 角色模拟：顶部角色切换器，不做真实认证

- **Decision**: 原型顶部提供「当前视角」切换器（银行业务部 / 机构业务部 / 证券公司业务部 / 客户经理 / 创新发展部 / 分公司只读 / 计划财务部只读），切换后按 FR-012 过滤可见入口与可执行动作（如非最高比例部门无部门间调整发起入口、客户经理仅见确认/退回）。A5 的公司统一身份认证在原型中以切换器示意。
- **Rationale**: 评审时需要快速演示「不同角色看到什么」；权限矩阵本身就是 FR-012 的验收内容，切换器让它可视化。
- **Alternatives considered**: 多开浏览器窗口模拟多人——否，演示成本高且无法展示互斥提示。

## D6. 数据持久化：内存为主，localStorage 快照为辅

- **Decision**: 运行时数据全部在内存对象（产品、配置版本、流程单、留痕、月度数据）；每次状态变更后序列化快照到 localStorage（单 key），刷新恢复；提供「重置演示数据」按钮回到种子态。留痕（FR-010）在原型中为只追加数组，界面上不提供任何修改/删除入口以示意「不可改删」。
- **Rationale**: 评审中途刷新不丢进度；重置按钮保证每轮演示从干净状态开始；只追加数组是最简单的不可变留痕模拟。
- **Alternatives considered**: 纯内存（刷新即丢）——否，长流程演示（部门间调整 5+ 环节）刷新丢失体验差；IndexedDB——否，复杂度不必要。

## D7. 在途互斥与状态联动（FR-013、FR-003、Edge Cases）

- **Decision**: 流程单集合上实施互斥检查：发起任何新流程前查该产品是否存在状态=在途的流程单，有则弹提示「该产品已有在途流程（场景 ×，发起人 ×），请先办结」。首次确认生效后产品状态字段 `新增→存量` 即时更新并在产品列表徽标区分；存量产品再发起首次确认被拒（US1-AS5）。
- **Rationale**: 互斥与状态流转是 spec 明确的阻止性校验，原型必须真实拦截而非仅文案示意。
- **Alternatives considered**: 仅灰置按钮不提示原因——否，验收场景要求「提示」。

## D8. E 清单未定稿项的原型口径：按 A3 建议默认演示并打标

- **Decision**: E-j（漏设沿用上月值+高亮、截止=拆分触发前、截止后改值触发重算提示）、E-k（按产品设置）、E-l（0%/100% 允许、100% 二次确认）全部按 spec A3 的建议默认实现；相关界面元素加「⚠ 待业务定稿（E-j/E-k/E-l）」小角标，评审时可口头确认，定稿后摘标或改行为。E-a~E-i 属拆分引擎边界，不在录入原型范围（预览遇除零走 D3 降级）。
- **Rationale**: A3 已声明「按建议默认执行，定稿后修订」；打标让原型同时承担「推动定稿」的评审职能，与例子表活文档方法论一致。
- **Alternatives considered**: 留空待定稿再实现——否，漏设/端点是评审必问场景，空着反而拖慢定稿。

## D9. 历史版本与留痕查询（FR-011、US5）

- **Decision**: 配置按月/按流程形成不可变版本（版本号、生效期间、快照行集）；提供「产品档案」视图：左侧版本时间线（含每次变更的谁/何时/场景/旧值→新值四要素，SC-005），右侧选中版本的归属比例条 + 与上一版 diff 高亮；留痕流水独立表格视图，支持按产品过滤，退回动作与意见在案（US5-AS2）。
- **Rationale**: SC-005 要求 1 分钟内定位四要素——版本时间线 + diff 是最直接的演示形态；与既有原型 splitBar 视觉语言复用。
- **Alternatives considered**: 仅留痕流水无版本对照——否，FR-011 明确要求「全部历史配置版本」。
