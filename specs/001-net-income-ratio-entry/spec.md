# Feature Specification: 专户产品净收入比例录入

**Feature Branch**: `001-net-income-ratio-entry`

**Created**: 2026-09-21

**Status**: Draft

**Input**: User description: "净收入比例录入"

## 背景与定位 *(informational)*

专户产品 KPI 净收入按「产品级配置」归属至市场总部部门（银行业务部、机构业务部、证券公司业务部）与分公司：每个产品一套「归属主体 × 比例」，合计 100%。本功能覆盖该配置的**全生命周期录入与确认**——新增产品首次确认、部门内调整（每月）、部门间调整（全年随时）、银行部总部份额设置，以及全程操作留痕。配置生效后作为下游「净收入拆分计算」的唯一比例来源。

术语以 `项目/净收入比例录入/CONTEXT.md`（已定稿术语表）为准；银行部拆分口径以 ADR-0001（混合模型：总部份额人工设置、剩余份额纯计算）为准。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 新增产品首次确认归属及比例 (Priority: P1)

某专户产品新成立、尚未在系统内确认过归属。牵头市场总部部门发起首次确认，编辑该产品的归属主体与比例（合计须为 100%），提交至客户经理确认；客户经理确认无误后配置生效，产品转为存量产品。若客户经理退回，发起人修改后重新提交。

**Why this priority**: 没有首次确认就没有任何产品级配置，拆分计算无从谈起——这是整个链路的数据源头，也是唯一能独立交付价值的最小闭环（一个产品的配置生效即可支撑该产品的拆分）。

**Independent Test**: 选取一个未确认的新增产品，走完「发起 → 编辑归属及比例 → 提交客户经理 → 确认无误 → 生效」全流程，验证配置落库、产品状态转为存量、操作留痕完整。

**Acceptance Scenarios**:

1. **Given** 一个尚未完成首次确认的专户产品，**When** 牵头市场总部部门发起首次确认并提交归属主体及比例（合计 100%），**Then** 流程进入客户经理确认环节，发起人与客户经理均可见流程状态。
2. **Given** 首次确认流程处于客户经理确认环节，**When** 客户经理点击「确认无误」，**Then** 配置生效、产品转为存量产品，操作留痕记录各环节操作人与时间。
3. **Given** 首次确认流程处于客户经理确认环节，**When** 客户经理「退回」并附意见，**Then** 流程回到发起人，发起人可修改后重新提交，退回原因留痕。
4. **Given** 编辑中的归属比例合计不等于 100%，**When** 发起人尝试提交，**Then** 系统阻止提交并提示差额。
5. **Given** 某产品已完成首次确认（存量产品），**When** 任何角色尝试再次发起「首次确认」，**Then** 系统拒绝并提示走调整流程。

---

### User Story 2 - 银行业务部按月设置总部份额 (Priority: P2)

银行部产品按月拆分前，银行业务部为名下产品设置「归属银行总部的份额」（按产品设置，每月可调）；界面展示「柜台管理费/总管理费」占比作为参考值，仅供参考、不自动采用。设置经审批通过后生效；剩余份额（1 − 总部份额）由系统按销量与管理费数据自动分配至各分公司，无人工干预。

**Why this priority**: 银行部产品是净收入体量最大的部分，总部份额是六条拆分规则中唯一的人工参数（ADR-0001 定稿口径）；但依赖 P1 已产生存量配置，故列 P2。

**Independent Test**: 对某银行部存量产品设置当月份额（如 20%），验证参考值仅展示不采用、审批通过后设置值生效、操作留痕；漏设场景验证沿用上月值并高亮提醒。

**Acceptance Scenarios**:

1. **Given** 某银行部存量产品，当月拆分计算尚未触发，**When** 银行业务部设置总部份额并提交审批、审批通过，**Then** 该份额作为当月拆分的总部占比生效。
2. **Given** 设置界面展示参考值（柜台管理费占比）与设置值不一致，**When** 审批通过，**Then** 以设置值为准，参考值不参与任何计算（ADR-0001 回归口径）。
3. **Given** 当月银行部未为某产品设置份额，**When** 拆分计算触发时点到达，**Then** 系统沿用该产品上月份额并在界面高亮提醒（假设 A3，待 E-j 定稿确认）。
4. **Given** 份额设置截止时点（拆分计算触发前）已过，**When** 银行部修改当月份额，**Then** 系统提示将触发当月拆分重算，确认后重算（假设 A3，待 E-j 定稿确认）。
5. **Given** 银行部尝试设置份额为 100%，**When** 提交，**Then** 系统要求二次确认（提示分公司份额将全部为 0）；0% 与 100% 端点值均允许（假设 A3，待 E-l 定稿确认）。

---

### User Story 3 - 机构/券商部门按月部门内调整 (Priority: P2)

机构业务部、证券公司业务部每月可调整本部门与分公司之间、或分公司之间的归属及比例：编辑归属主体（增删）与比例数值，提交审批，通过后当月生效。

**Why this priority**: 与 US2 同为「部门内调整·每月」的常态操作，覆盖另外两家市场总部部门；操作对象是完整的归属及比例（不同于银行部的单一份额参数）。

**Independent Test**: 对某机构部存量产品发起部门内调整：新增一个分公司归属主体并重新分配比例，提交审批通过，验证新配置生效、旧配置留档、留痕完整。

**Acceptance Scenarios**:

1. **Given** 某机构部存量产品的现行配置，**When** 发起人编辑归属主体与比例（合计 100%）并提交审批、审批通过，**Then** 新配置生效，生效前的配置版本可追溯。
2. **Given** 调整单处于审批环节，**When** 审批人「退回发起人」，**Then** 调整单回到可编辑状态，现行配置保持不变，退回意见留痕。
3. **Given** 调整删除了某归属主体，**When** 提交，**Then** 系统校验剩余主体比例合计仍为 100%，否则阻止提交。

---

### User Story 4 - 部门间调整（跨部门归属变更） (Priority: P3)

涉及多个市场总部部门的归属及比例调整，全年随时可发起：由该产品**当前归属比例最高的部门**发起，提交后涉事部门逐一线上确认（同意/退回），全部同意后由创新发展部归口审批，通过后调整生效。

**Why this priority**: 频次低于部门内调整（每月）但争议性最高，需要多方线上确认与归口把关；流程依赖 P1–P3 已建立的配置与流程机制。

**Independent Test**: 构造一个归属涉及两个总部部门的产品，由比例最高部门发起调整，验证：非最高比例部门无发起入口、涉事部门确认与退回路径、创新发展部归口通过后生效、全程留痕。

**Acceptance Scenarios**:

1. **Given** 某产品归属涉及银行业务部（60%）与机构业务部（40%），**When** 银行业务部发起部门间调整，**Then** 流程进入机构业务部线上确认环节。
2. **Given** 机构业务部尝试对同一产品发起部门间调整（自身非最高比例部门），**When** 进入发起入口，**Then** 系统拒绝并提示仅当前归属比例最高的部门可发起。
3. **Given** 某涉事部门「退回」，**When** 退回发生，**Then** 流程整体退回发起方修改，重新走确认链；退回意见留痕。
4. **Given** 全部涉事部门确认同意，**When** 创新发展部归口审批通过，**Then** 调整生效，新配置作为下一次拆分计算的比例来源。

---

### User Story 5 - 操作留痕与配置追溯 (Priority: P4)

所有录入、调整、确认、审批操作跨场景累积留痕：记录操作人、角色、时间、场景、变更前后值（归属主体与比例的旧值/新值）。授权用户可按产品查看现行配置与全部历史版本。

**Why this priority**: 支撑考核争议回溯与审计，是管理要求而非拆分计算的直接输入；但所有前序故事的验收都依赖它，故随各流程内建、独立故事化以便验收。

**Independent Test**: 完成任意一次配置变更后，按产品查询操作记录与历史版本，验证变更前后值、操作人、时间、场景完整可查。

**Acceptance Scenarios**:

1. **Given** 某产品经历了首次确认与两次调整，**When** 授权用户查询该产品的配置历史，**Then** 可见三个版本及每次变更的明细（谁、何时、改了什么、旧值/新值）。
2. **Given** 任一流程环节发生退回，**When** 查询操作记录，**Then** 退回动作与退回意见同样在案。

---

### Edge Cases

- 比例合计不等于 100%（含删除归属主体后）：一律阻止提交并提示差额。
- 总部份额端点值 0% / 100%：均允许；100% 需二次确认（分公司份额全为 0）。
- 当月漏设总部份额：沿用上月值 + 界面高亮提醒（E-j 建议默认，待业务定稿）。
- 份额设置截止后改值：触发当月拆分重算（E-j 建议默认，待业务定稿）。
- 总管理费为 0 导致参考值算不出：界面显示「参考值不可用」而非空白或报错（E-g 关联小尾巴，待业务定稿）。
- 同一产品同时存在两个进行中的调整流程：后发起者被阻止，提示已有在途流程（配置互斥）。
- 部门间调整在途时，涉事产品的月度拆分计算触发：按触发时点的**已生效**配置计算，在途调整不影响当月结果。
- 新增产品首次确认在途、但当月净收入（总）已上传：拆分计算跳过未生效配置的产品，待首次确认生效后按重算机制处理。
- 审批人/确认人长时间未处理：流程保持待办状态并可见催办入口（不设自动通过）。
- 归属主体（分公司）在主数据中被撤销：存量配置含该主体时提示需走调整流程更换，不静默删除。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 按「产品级配置」管理归属及比例：每个专户产品独立一套「归属主体 × 比例」，归属主体限定为市场总部部门（三家）或分公司；不存在跨产品共用的部门级统一比例。
- **FR-002**: 系统 MUST 强制校验同一产品全部归属主体的比例合计为 100%，不满足时阻止提交并提示差额。
- **FR-003**: 系统 MUST 区分产品状态：未完成首次确认的为新增产品，完成后的为存量产品；首次确认生效后产品状态 MUST 自动转为存量。
- **FR-004**: 新增产品首次确认 MUST 支持流程：牵头市场总部部门发起并编辑归属及比例 → 提交至客户经理确认（确认无误 / 退回）→ 确认后生效；退回后发起人可修改重提。
- **FR-005**: 部门内调整 MUST 按月开放给三家市场总部部门，且按部门区分操作形态：银行业务部仅设置「总部份额」单一参数；机构业务部与证券公司业务部可编辑本部门与分公司之间、或分公司之间的归属主体及比例。
- **FR-006**: 银行部总部份额 MUST 按产品设置、每月可调；设置界面 MUST 展示「柜台管理费/总管理费」占比作为参考值，参考值 MUST NOT 被自动采用（ADR-0001 定稿口径）。
- **FR-007**: 部门内调整 MUST 经审批（提交审批 → 审批通过 / 退回发起人）后生效。
- **FR-008**: 部门间调整 MUST 全年随时可发起，且发起资格 MUST 限定为该产品当前归属比例最高的市场总部部门；流程为：发起 → 涉事部门线上确认（同意 / 退回）→ 创新发展部归口审批 → 生效；任一环节退回则整体退回发起方。
- **FR-009**: 配置变更生效时点 MUST 与月度拆分计算衔接：拆分计算触发前生效的配置参与当月拆分；触发后变更当月值的，MUST 触发当月拆分重算（假设 A3）。
- **FR-010**: 系统 MUST 对所有录入、调整、确认、审批、退回操作留痕：操作人、角色、时间、场景、变更前后值；留痕记录 MUST 不可修改与删除。
- **FR-011**: 系统 MUST 支持按产品查询现行配置与全部历史配置版本，供考核争议回溯与审计。
- **FR-012**: 系统 MUST 按角色控制操作权限：各市场总部部门仅可操作本部门职责内的流程；客户经理仅可执行首次确认的确认/退回；创新发展部仅可执行部门间调整的归口审批；计划财务部不在本功能内操作配置。
- **FR-013**: 同一产品同一时间 MUST 至多存在一个在途配置变更流程；已有在途流程时阻止新流程发起并提示。
- **FR-014**: 生效配置 MUST 作为下游净收入拆分计算（产品 × 归属主体份额）的唯一比例来源输出。
- **FR-015**: 「考核数据确认」（年度追溯性确认、异议重算、双批准）MUST NOT 纳入本期范围（2026-09-21 用户决定挂起）；本功能仅通过配置历史版本与操作留痕（FR-011、FR-010）为其未来立项提供数据基础。
- **FR-016**: 录入与调整界面（首次确认、银行部总部份额设置、机构/券商部门内调整、部门间调整）MUST 内建「拆分结果实时预览」：按当前编辑中的配置对上月净收入（总）试算各归属主体份额，仅展示、不落库；银行部场景预览 MUST 同时展示总部份额（设置值）与剩余份额按规则链分配至各分公司的试算结果。
- **FR-017**: 预览 MUST 与正式拆分计算采用同一规则口径（R1–R3/R5/R6 规则链），确保「所见即所拆」；预览结果 MUST 明确标注为试算值，MUST NOT 被任何下游流程引用或落库。
- **FR-018**: 当上月净收入（总）尚未上传、或该产品无净收入数据时，预览 MUST 显示「暂无可预览数据」并说明原因，录入与调整流程本身 MUST NOT 被阻塞。

### Key Entities *(include if feature involves data)*

- **专户产品**: 配置的载体。关键属性：产品代码、产品名称、新增/存量状态、牵头市场总部部门。产品信息由外部产品系统同步，本功能只读引用。
- **归属配置（产品级）**: 某产品在某生效期间的「归属主体 × 比例」集合，合计 100%。按月形成版本，历史版本不可变、可追溯。
- **总部份额**: 银行部产品的人工参数，按产品 × 月份记录设置值、参考值（柜台管理费占比）、设置人与审批状态。
- **流程单**: 一次配置变更的流转实例。关键属性：场景（首次确认 / 银行部部门内 / 机构券商部门内 / 部门间）、发起人、当前环节、状态（在途 / 生效 / 退回关闭）、涉事确认方、审批方。
- **操作留痕**: 跨场景累积的操作记录。关键属性：操作人、角色、时间、所属流程单、动作（录入 / 提交 / 确认 / 退回 / 审批 / 生效）、变更前后值。
- **角色**: 银行业务部、机构业务部、证券公司业务部、分公司（只读）、客户经理、创新发展部（归口）、计划财务部（下游，不操作配置）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 单个产品的首次确认（发起至客户经理确认生效）可在 1 个工作日内线上完成，替代现行线下人工打标签。
- **SC-002**: 比例合计不为 100% 的配置提交被 100% 拦截，生效配置中不存在合计≠100% 的记录。
- **SC-003**: 银行部当月全部产品的总部份额设置（含审批）在拆分计算触发时点前完成率 100%；漏设产品数每月为 0（高亮提醒兜底）。
- **SC-004**: 部门间调整自发起至生效全程线上完成，任一环节的确认/退回均有留痕，线下沟通仅作为催办手段。
- **SC-005**: 任意一次配置变更可在 1 分钟内定位到「谁、何时、什么场景、旧值/新值」四要素。
- **SC-006**: 月度拆分计算所采用的比例与当时已生效配置 100% 一致（配置-计算零偏差）。
- **SC-007**: 上线后 3 个月内，因归属/比例配置错误引发的拆分结果异议次数较人工打标签时期下降 50% 以上。

## Assumptions

- **A1（范围）**: 净收入（总）的每月上传（计划财务部）与拆分计算引擎（R1–R3 直销/代销/混合规则链、R5 匹配拆分、R6 总部份额计算）分别为本功能的上游输入与下游消费方，不在本 spec 范围内；本功能只保证「生效配置」这一契约的输出（FR-014）。
- **A2（主数据）**: 产品信息表由产品系统接口同步；地区→分公司映射、分公司代码、代销渠道清单等主数据由银行业务部在外部维护，本功能只读引用。
- **A3（E 清单建议默认）**: 尚未与银行业务部定稿的边界项按例子表建议默认执行，定稿后若有出入以定稿为准并修订本 spec：E-j 漏设份额沿用上月值+高亮提醒、设置截止=拆分计算触发前、截止后改值触发重算；E-k 总部份额按产品设置；E-l 端点 0%/100% 均允许、100% 需二次确认。
- **A4（牵头部门）**: 新增产品的「牵头市场总部部门」由业务发展线下确定，系统发起时允许在三家市场总部部门中选择，不做自动判定。
- **A5（身份与权限）**: 用户为公司内部角色，复用公司统一身份认证与组织架构数据；角色-部门归属以组织架构为准。
- **A6（审批链）**: 部门内调整的审批人为发起部门指定的固定审批角色（每部门一至两人），审批链不需按金额/比例动态变化。
- **A7（生效语义）**: 「生效」指配置成为下一次拆分计算触发时的比例来源；月中生效的部门间调整自当月起适用（若在计算触发前）。
