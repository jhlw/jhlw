# 需求资产库设计方案

- 日期：2026-09-29
- 角色：需求分析人员（基金公司内部）
- 状态：已评审通过（会话内三节分节确认）

## 1. 背景与目标

历史项目的业务需求文档散落在工作区子项目目录与外部（公司共享盘等），格式异构（xlsx / xmind / pdf / docx / 流程图截图），存量几十到上百份，且随项目持续新增。每次新需求分析都从零开始，历史口径、流程定义、踩过的坑无法复用。

本方案建立**需求资产库**：把历史需求文档输入并结构化，作为以后一切需求分析（参照同类、规则提炼、AI 分析上下文、决策追溯）的基础资产。

**四种核心用途**（均已确认为设计目标）：

1. **新需求参照同类历史**——新需求来了，按业务域快速找到同类历史需求的口径、流程、范围定义
2. **提炼业务规则库**——从需求实例提炼跨项目通用规则、术语口径
3. **喂 AI 做分析上下文**——需求拷问、写 spec、生成测试要点时，先查库再动笔
4. **决策追溯**——任何规则能回溯到当初哪个项目、哪份文档、哪个位置定的

**方案选型**：三选一评审通过 Markdown 资产库 + 入库 skill（方案一）。落选：YAML/JSON 双轨（维护成本高、量级用不上）、Excel 台账（长文本规则表达弱、AI 消费差、不可 git diff）。

## 2. 资产库结构与模板

**位置**：仓库根 `docs/需求资产库/`（跨项目资产，不挂任何单一子项目）。

```text
docs/需求资产库/
├── 索引.md                      # 唯一检索入口：项目×业务域×文档 + 关键词
├── 待处理/                      # 投喂区：外部文档先丢这里，skill 处理完归档
├── 项目/<项目名>/
│   ├── 源文档/                  # 原始文件归档（保真，不改名，可加日期后缀）
│   ├── <文档名>.结构化.md       # 每份源文档 ↔ 一条结构化条目（一一对应）
│   └── README.md               # 项目内导航：本项目有哪些文档、什么结论
└── 规则库/
    ├── <业务域>.md              # 如 KPI核算.md、信息披露.md
    └── README.md               # 规则总目录 + 冲突清单
```

### 2.1 结构化条目模板

frontmatter + 固定七章：

```markdown
---
项目: 净收入比例录入
业务域: KPI核算            # 受控词表：估值核算/信息披露/注册登记/KPI核算/…
文档类型: 业务需求书        # 业务需求书/流程说明/澄清问答/会议纪要
源文档: 源文档/专户产品KPI…20260303.xlsx
结构化日期: 2026-09-29
状态: 草稿                  # 草稿 → 已审校 / 存疑
---
## 1. 需求背景与目标
## 2. 干系人与角色
## 3. 核心流程（步骤/状态流转）
## 4. 业务规则          ← 逐条编号（R-01…），规则库的抽取源
## 5. 数据对象与口径
## 6. 边界与异常场景
## 7. 未决问题与历史澄清
```

### 2.2 规则库条目

全局唯一 ID = 业务域前缀 + 序号，每条带溯源与冲突登记：

```markdown
## KPI-003：净收入按确认流程拆分后，比例合计必须 = 100%
- 适用范围: 专户产品
- 溯源: [净收入比例录入/需求20260303] Sheet「拆分规则」
- 冲突: 无   ← 口径不一致时写对方规则 ID + 待裁定标记
```

### 2.3 结构要点

- **每文档一条**而非每项目一条——溯源粒度到文档，条目与源文件一一对应
- **业务域受控词表**（借用产品画像谱系的大类），保证索引与规则库按域聚合不散
- **状态字段**区分 AI 草稿与人工审校——质量闸门：未审校条目的规则不进规则库
- 规则冲突显式登记在 `规则库/README.md`，待业务裁定后修订

## 3. 入库管道（/需求入库 skill）

**skill 形态**：项目级 skill，放仓库 `.claude/skills/需求入库/`（与资产库强绑定，不装用户级）。

### 3.1 流程

```text
待处理/ 扫描
   │ 按格式分发读取：
   │   xlsx → openpyxl 逐工作表（处理合并单元格/隐藏表）
   │   pdf  → 文本层提取，扫描件走 OCR
   │   docx → pandoc 转 Markdown
   │   xmind → zip 解包解析 content.json（新版）/ content.xml（旧版）
   │   图片（流程图截图）→ 视觉模型读图转文字描述
   ▼
逐份：判定项目归属（并入已有 / 新建项目目录）
   → 生成结构化条目（状态: 草稿）
   → 源文档移入 项目/<项目名>/源文档/
   ▼
输出处理报告：成功清单 + 存疑清单（读不懂/格式损坏/归属不明）
   ▼
人工审校条目 → 状态: 已审校
   ▼
规则抽取（审校后触发）：从「业务规则」章节提炼
   → 与规则库比对：语义相同 → 合并（多挂一条溯源）
                 不同   → 登记冲突到规则库 README
   → 更新 索引.md
```

### 3.2 三条质量铁律

1. **禁止编造**——源文档没有的内容，字段写「存疑」留人工，不猜
2. **溯源到文档内位置**——Sheet 名 / 页码 / 章节号，不接受只写文件名
3. **未审校不入库**——规则抽取只吃「已审校」条目，草稿规则不进规则库

### 3.3 增量惯例

每个项目收尾时，把需求类文档丢 `待处理/` 跑一次 skill，沉淀为例行动作。

## 4. AI 消费方式与维护约定

### 4.1 四种用途的落地机制

| 用途 | 落地机制 |
|------|----------|
| 新需求参照历史 | 需求类任务（specify / 需求拷问 / 测试要点）开始前，先查 `索引.md` 按业务域取相关条目注入上下文 |
| 喂 AI 做上下文 | 在 `docs/agents/domain.md`（multi-context 域文档）登记资产库为需求类任务**必查源**；skill 里写明"先查库再动笔" |
| 规则库引用 | 写 spec / 口径定义时直接引规则 ID（如 `KPI-003`），规则文本可整条嵌入 |
| 决策追溯 | 双保险：git log（谁何时改）+ 溯源链（规则 → 项目 → 文档 → Sheet/页码） |

### 4.2 维护约定

1. `索引.md` 唯一入口，由入库 skill 维护；业务域受控词表增删需人工定
2. 规则修订 = **新增新条目 + 旧条目标记「已废弃 → 由 XX-NNN 取代」**，不原地改语义（保住追溯链，与需求拷问题库"只增不删"哲学一致）
3. `CONTEXT-MAP.md` 加一行指向资产库

## 5. 实施顺序

1. **建骨架**：目录 + 模板 + 索引 + `/需求入库` skill
2. **试点跑通**：用工作区现有文档验证——净收入比例录入那组（xlsx + xmind + pdf 三种格式全齐）
3. **外部存量分批导入**：几十上百份分批投喂、审校，不追求一次到位
