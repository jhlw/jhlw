## 二、全书框架：三部分 18 章

```
第一部分 开始（第1-4章）      为什么 + 总览 + 导入策略
第二部分 关键过程模式（第5-11章）  七个模式逐个展开 —— 全书核心
第三部分 案例研究（第12-17章）    六个团队的完整历程
                              （第18章 思想总结 + 附录 资源）
```

第一部分回答"为什么"：交付速度时代，"正确地构建产品"和"构建正确的产品"是两码事——技术实践管前者，本书管后者。核心主张（第 20 页）：

> **功能需求、需求说明和验收测试都是同一份东西。** 其结果是一个活文档系统，它和代码一样确切可靠，但更容易理解。

四个主要优点（第 1 章）：更有效地实施变更、更高的产品质量、减少返工、更好的协作。

## 三、核心：七个关键过程模式（第 2 章总览，第 5-11 章展开）

一个需求在这条链上逐步演化：**业务目标 → 范围 → 关键实例 → 带实例的需求说明 → 可执行的需求说明 → 活文档**（第 2.8 节有完整贯穿示例）。

### 模式 1：从目标中获取范围（第 5 章）
范围不是需求清单堆出来的，是从业务目标推导出来的。关键提问：
- 理解"为什么"和"谁"——这项功能为什么有用？谁用？
- 价值从何而来？业务用户预期的输出是什么？
- 询问替代方案；不要只顾最低层次的需求；确保交付完整功能

### 模式 2：协作制定需求说明（第 6 章）
三方（业务 + 开发 + 测试）同时在场写例子，杜绝信息串行传递失真。五种协作模型：
- 大型全体工作坊（所有人）
- **小型工作坊"神勇三剑客"**（three amigos：每方一人）
- 结对编写 / 迭代前频繁审查测试 / 非正式交谈

准备要领：只准备初始实例、**不要让过度的准备阻碍了讨论**。

### 模式 3：举例说明（第 7 章）——对你最有用的一章
关键实例的四条标准 + 非功能需求：

| 标准 | 反模式 |
|---|---|
| **精确到位** | 不要"是/否"式回答；避免抽象等价类（"金额 A""用户 B"） |
| **完整** | 用数据作试验；用替代方法检验同一功能 |
| **真实** | 避免虚构数据——直接从客户那里获得基本例子 |
| **易于理解** | 避免穷举所有组合；寻找隐含概念（边界例代表的规则要命名） |

非功能需求（7.6）：性能需求要精确到数、UI 用低保真原型、讨论用核查清单、建立参照例子。

### 模式 4：提炼需求说明（第 8 章）——好书/坏书对照 + 18 条提炼规则
第 8.1/8.2 用同一需求（免费送货服务）给出好、坏两版规格对照，8.3 列 18 条规则，按用途归组：

**写给谁（可读性）**：实例精确可测；需求说明不言自明；叙述性标题+短篇幅讲目标；使用领域语言；**展示给别人看并保持沉默**（对方不问就能看懂才算过关）
**写什么（内容边界）**：脚本不是需求说明；不用流程式描述；关注业务功能而非软件设计；不与代码耦合；不含技术临时方案；不陷入 UI 细节；不要过度定义实例；需求说明要专注
**怎么组织（结构）**：从简单例子入手逐步展开；使用 **Given-When-Then** 语言；不明确建立所有依赖（缺省值放自动化层）；但不要总是依赖缺省值

### 模式 5：自动化验证而不修改需求说明（第 9 章）
- 自动化层是代码资产，不是二等公民；**不要在自动化层里复制业务逻辑**
- 沿系统边界自动化、在应用表皮之下测业务逻辑；UI 只测 UI 功能
- 测试数据：避免预填充数据，引用数据可预填充

### 模式 6：频繁验证（第 10 章）
持续集成环境下让可执行规格随时可跑：解决不稳定测试（等事件而非等时长、外部系统用测试替代品、多级验证）；更快反馈（业务时间、快慢测试分开、并行）；管理失败测试（已知失败包、自动检查被禁用测试）。

### 模式 7：演化出文档系统（第 11 章）
活文档三属性：**易于理解**（不冗长、寻找更高层次概念）、**前后一致**（演化出统一语言并协作定义——与你的术语表实践直接接轨）、**组织有序**（按功能区域/业务流程组织，而非按用户故事堆积）。最后一节"聆听活文档"：规格混乱是系统设计问题的信号。

## 四、第 4 章速览：导入策略与警告信号（国内落地最实用）

- 五个切入点：作为更大过程变更的一部分 / 从提高质量切入 / 从功能测试自动化起步 / 引入可执行说明工具 / 以 TDD 为踏脚石
- 文化策略：避免"敏捷"术语、确保管理层支持、把 SBE 当"比执行验收测试更好的方式"推销、不要太关注工具
- **五个警告信号**：频繁改动的测试、回退、组织级失调、"以防万一"的代码、霰弹式修改——出现任何一个说明实践走样了

## 六、批判性阅读提示（BA 视角）

1. **翻译**：拗口处对照英文术语；豆瓣书评建议先了解 BDD/ATDD 概念再读（BDD 描述需求，ATDD 侧重测试自动化，本书以前者为出发点）
2. **敏捷语境**：书中默认短迭代、业务方随时可参与。传统金融机构未必满足——第 5~8 章（目标→协作→举例→提炼）**不依赖敏捷，可全量取用**；第 9~10 章（自动化、频繁验证）视开发团队条件裁剪；这正是精读指南（lessons/01）把"三栏例子表 + 手工执行"作为起步的原因
3. **啰嗦是设计**：多条书评嫌"啰嗦"——因为全书刻意不用代码和工具，靠重复讲清理念；速读时可跳过案例细节直接看每章末"铭记"小结
4. **与你既有资产的映射**：三栏例子表 ↔ 第 7 章四条标准；例子表"暴露的边界类型"列 ↔ 第 7.5 节"寻找隐含概念"；术语表 ↔ 第 11 章"演化出一种语言"；题库追问链走到底 ↔ 关键实例
